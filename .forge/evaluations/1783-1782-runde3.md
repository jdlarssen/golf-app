### Verifisering mot de fem punktene

**1. Shape-endring only — feilkoder og første-feil-rekkefølge uendret. BEKREFTET.**

Rekkefølgen på feilkodene i `parseCupPlanForm`, ekstrahert mekanisk fra begge
versjonene, er identisk:

```
gammel: 'plan_preset' 'plan_strategy' 'plan_sessions' 'plan_sessions'
ny:     'plan_preset' 'plan_strategy' 'plan_sessions' 'plan_sessions'
```

`plan_best_ball` kommer fra `parseBestBall`, og kallstedet ligger i begge versjoner
etter customSessions-blokka og før suksess-returen — posisjonen er uendret.

Hver endret linje i `planValidation.ts` er en `return`-setning eller en type-annotasjon.
Selve betingelsene er byte-identiske: `cleaned === ''`, `!Number.isInteger(n) || n < 0
|| n > 100` (kun klammer lagt til), `!VALID_PRESET_IDS.has(presetId)`,
`strategy !== 'handicap' && strategy !== 'random'`, og array/JSON-sjekkene. Den ene
betingelsen som med vilje er endret er diskrimineringen selv:
`'error' in bestBall` → `!bestBall.ok`.

Intern helper `parseBestBall` er unifisert i samme slengen
(`{ ok: number | null } | { error }` → `{ ok: true; value } | { ok: false; error }`), så
modulen ender ikke halvt-og-halvt slik kontrakten krever. Den nye eksporterte typen
`CupPlanParseResult` speiler søsken-idiomet `CupDraftParseResult`
(`parseCupDraftForm.ts:77-79`) felt for felt, inkludert `values`-navnet.

*Positivt funn (ingen handling):* gammel `parseBestBall` la tallet i `.ok`, så `0` var
en falsy suksessverdi — en `!x.ok`-sjekk mot den gamle formen ville vært en bug. Den nye
formen flytter tallet til `.value` og lar `.ok` være ren boolean, så kallstedets
`!bestBall.ok` er trygt. Dekket av den grønne `['0', 0]`-testen.

### Funn

**NIT — `lib/cup/actions.ts:751` + T1 (bryter ikke kriteriet).**
`grep -rn "'error' in" lib/cup/` gir fortsatt ett treff:
`if ('error' in plan) return { error: plan.error };`. Dette er IKKE et parser-resultat —
`planCupMatchSwap` (`actions.ts:472`) returnerer
`Promise<SwapPlan | { error: string }>`, altså lese-/valideringsfasen for et
spillerbytte, ikke en skjema-parser. T1 krever «ingen treff på parser-resultater», og
det holder. Kontraktens problemformulering gjelder eksplisitt «to skjema-parsere», så
denne unionen er utenfor #1783. Verdt å vite at `'error' in`-idiomet dermed fortsatt
lever i `lib/cup/` for én ikke-parser-union; hvis eieren vil ha idiomet helt ensrettet
er det et eget, lite oppfølgingsissue — ikke noe som skal smyges inn i denne PR-en (I4).

**Ingen MUST-FIX.**
